# Advanced Stats — Read API Contract

Phase 5 exposes owner-only, backend-derived Advanced Stats data. Frontend rendering is intentionally deferred to Phase 6.

## Authentication and ownership

Every endpoint:

1. requires the normal ClashPanel authenticated session;
2. accepts a `playerTag` / legacy `playerID` request field;
3. verifies that the player is already linked to the authenticated ClashPanel account;
4. resolves the user's own `advanced_stats_tracking.id` server-side;
5. never accepts a caller-supplied tracking UUID.

A `STOPPED` tracker remains readable because stop preserves collected history. Deleting Advanced Stats data removes the history and makes these endpoints return `ADVANCED_STATS_NOT_ENABLED`.

## Periods

Supported values:

```text
7d
30d
90d
all
```

Missing/blank period defaults to `all`.

For 7/30/90 days, the backend computes one exact UTC instant from the request-time clock. Overview, units, armies, battles and trends all use that same lower boundary.

When the Clash API did not provide a real battle timestamp, Advanced Stats uses the first `observed_at` timestamp. This is the same upstream limitation documented in `advanced-stats-phase3-api-notes.md`.

## POST /AdvancedStatsOverview

Request:

```json
{
  "playerTag": "#ABC123",
  "period": "30d"
}
```

Response envelope:

```json
{
  "playerTag": "#ABC123",
  "status": "ACTIVE",
  "period": "30d",
  "from": "2026-07-08T14:00:00Z",
  "data": {
    "tracking": {},
    "summary": {},
    "favorites": {}
  }
}
```

Summary fields:

- attacks
- averageStars
- averageDestruction
- threeStarRate
- goldLooted
- elixirLooted
- darkElixirLooted

Favorite sections:

- troop (`TROOP` + `SUPER_TROOP`)
- spell (`SPELL`)
- siege (`SIEGE`)
- army

The favorite army is ranked primarily by battle count within the requested period.

## POST /AdvancedStatsUnits

Request:

```json
{
  "playerTag": "#ABC123",
  "period": "90d",
  "category": "TROOP"
}
```

`category` is optional. `ALL`/blank returns all categories.

Supported categories are the existing `AdvancedStatsUnitCategory` values:

```text
TROOP
SPELL
SIEGE
SUPER_TROOP
CLAN_CASTLE_TROOP
CLAN_CASTLE_SPELL
HERO
PET
EQUIPMENT
```

Each item contains:

- stable unit key
- current stored name
- category
- totalQuantity
- battlesPresent
- usageRate (percentage of tracked attacks in the period containing that unit)
- firstSeenAt
- lastSeenAt

## POST /AdvancedStatsArmies

Request:

```json
{
  "playerTag": "#ABC123",
  "period": "30d",
  "limit": 20
}
```

Default limit: 20. Maximum: 100.

Each army contains:

- armyHash
- normalized army payload
- battleCount
- averageStars
- averageDestruction
- firstSeenAt
- lastSeenAt

Phase 5 adds `army_hash` and `normalized_army_json` to each processed battle so period-specific army rankings are mathematically derived from battles in that period rather than from lifetime aggregate rows.

## POST /AdvancedStatsBattles

Request:

```json
{
  "playerTag": "#ABC123",
  "period": "30d",
  "limit": 25,
  "cursor": null
}
```

Default limit: 25. Maximum: 100.

Pagination is cursor-based, ordered descending by:

```text
(effective battle time, battle UUID)
```

The cursor is opaque URL-safe Base64 generated by the backend. The frontend must not construct or modify it.

Response:

```json
{
  "playerTag": "#ABC123",
  "status": "ACTIVE",
  "period": "30d",
  "from": "...",
  "limit": 25,
  "items": [],
  "hasMore": true,
  "nextCursor": "..."
}
```

Each battle exposes graph/history-safe fields only, including:

- battleAt
- timestampSource (`BATTLE` or `OBSERVED`)
- battleType
- opponent metadata
- player/opponent Town Hall when known
- stars
- destructionPercentage
- loot totals
- bootstrapImport
- armyHash
- normalized army
- parsed units

Raw authorization, API payloads and secrets are never returned.

## POST /AdvancedStatsTrends

Request:

```json
{
  "playerTag": "#ABC123",
  "period": "7d"
}
```

Returns UTC daily points with:

- date
- attacks
- averageStars
- averageDestruction
- threeStarRate
- goldLooted
- elixirLooted
- darkElixirLooted

The period boundary is applied to individual processed battles before grouping into dates. Therefore the first UTC day can be a partial day, but it cannot include attacks that fall outside the requested exact lookback.

## Processing filters

Read statistics only include rows where:

```text
is_attack = true
processing_status = PROCESSED
```

Therefore:

- defenses are not mixed into attacking-army statistics;
- `PARSER_ERROR` battles do not corrupt aggregates/read models;
- pending/ignored rows are excluded.

## Database exposure

All Phase 5 read functions are `security definer` functions with execution revoked from:

```text
public
anon
authenticated
```

Only `service_role` receives execute permission.

The browser therefore still talks only to ClashPanel's Java backend.

## Phase 6 note

The eleven lifecycle/read route constants remain backend-local through Phase 5. Phase 6 must mirror the routes into the shared frontend endpoint configuration and let `scripts/check-endpoints.mjs` verify the browser/backend contract before the UI is considered complete.
